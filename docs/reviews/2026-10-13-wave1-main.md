### Unknown two_handed outside the main hand is treated as one-handed: configuration is Valid, Complete and definitive
- Area: gear; location `crates/core/src/gear/configuration.rs:230`; upheld as blocker; on c357bf1: Open (file unchanged since 08f6daa).
- Expected vs actual: Expected: an item whose two_handed is unknown/unsupported/restricted placed in any hand slot other than main_hand (with or without a main-hand partner) is Uncertain with CertaintyReason::UnknownTwoHanded, never Valid, and top_is_definitive is false (AGENTS.md: Unknown is never coerced; plan 18.4: unknown required inputs never become a definite affirmative; M5 acceptance: invalid configurations rejected). - Correction: In classify(), for every placed item in a hand slot other than hands.main_hand whose two_handed is unavailable, set validity Uncertain and push UnknownTwoHanded (the symmetric counterpart of TwoHandedOutsideMainHand). Extend assert_constraints to treat unavailable two_handed as forbidden in the valid list (off-hand slot, or main hand with a partner), and add a regression test plus a fixture variant with the mystery item in the off-hand.

### recommendation_data publishes proposed/baseline scores as Known even when the breakdown is Low certainty (unknown attributes counted as 0)

Add a test showing that a demo summary and a reference summary with equal character and session IDs are both Inserted, and that equal keys in one context still produce Unchanged or Conflict.

### Any reminder shown without a trusted clock is suppressed permanently, even after re-arm and a later trusted clock
- Area: reminders-sessions; location `crates/core/src/reminders.rs:605`; upheld as important; on c357bf1: Open (file unchanged since 08f6daa).

### Cycle detection ignores eligibility and objective_state, so real acceptance deadlocks pass validation

### A participant with unknown access, choice or sibling prerequisites is reported as Behind, with a catch-up path that may not exist
- Area: travel-eligibility; location `crates/core/src/eligibility.rs:774`; upheld as important; on c357bf1: Open (file unchanged since 08f6daa).
- Expected vs actual: Expected: the catch-up interpretation is offered only when every other component is known to pass. In `unmet()` of an All, include Unknown siblings, or mark the tree incomplete. Update `required_chain_false_dominates_unknown` and tighten the property test: when any input is unknown, the result must not be Behind unless every unknown component lies inside the catch-up tree.

### A reset-bound quest that is known turned in is Eligible with no reason
