# Review: G5b data and system screens (PR #162)

## Verdict

No blocker. The six screens keep their accessible names, roles and heading outline, and the
named refresh-tick bug is genuinely fixed (both new tests fail on the old SettingsScreen). Two
important Settings defects remain in the new dirty-draft logic, one important layout regression
(horizontal overflow at 320 px / 200 % text on two screens), and some smaller points.

## Findings

### Important

**I1. A failed or conflicting save is a dead end: the stale revision is never adopted.**
`apps/desktop/src/screens/SettingsScreen.tsx:42-47`, `:60`.
While the draft is dirty, every refresh keeps `old.record` (the revision the edits were made
against). If the store changed, Save sends `expected_revision` = old revision and the backend
rejects it ("Stale settings"; the Rust CAS is real, `crates/app/tests/today.rs:382-389`).
Nothing resets `dirty` after that failure, so each later refresh again keeps the stale record
and every later Save fails the same way. There is no "reload stored values", "discard edits" or
"apply my edits to the new revision" action; only leaving the screen recovers, and then the
edits are lost. Also `setError("")` at line 34 runs on every tick, so the conflict message
vanishes within 60 s while the form silently stays unsaveable.
Reproduced with a throwaway vitest (deleted): dirty edit, store revision 1 to 2, tick, Save,
tick, Save: `expected_revision` sent `[1,1]`, alert "Stale settings" both times.
Fix: on a conflict (or whenever a background refresh finds `settings.value.revision !==
old.record.revision` while dirty) show a persistent notice with two explicit actions, "Keep my
edits and save over the newer settings" (adopt the new revision, keep the draft) and "Discard my
edits" (take the stored draft, clear `dirty`). Do not clear the error on a background tick.
Add unit tests for: conflict then recover, and that the conflict message survives a tick.

**I2. A refresh tick that lands while a save is in flight drops the save result and leaves the
draft dirty on a stale revision.**
`SettingsScreen.tsx:26`, `:49`, `:56`, `:61`.
The refresh effect does `++ticket.current`, which invalidates the in-flight `save()`
(`mine !== ticket.current` returns early). The write was committed by the backend, but the
screen never runs `dirty.current = false`, `setLoaded(result)`, the "saved" status message, or
`onChanged()`. The refresh response then sees `dirty` still true and keeps the old record, so
the next Save sends the pre-save revision and fails (I1). On origin/main this race also dropped
the result but self-healed because the refresh replaced the draft; the new retention makes it
sticky. Consequence: contrast/text-size changes are not applied by `onChanged()`, no
confirmation, and a later Save conflicts with the user's own earlier save.
Reproduced with a throwaway vitest (deleted): Save, rerender with `refreshKey+1` before the
update resolves, resolve: `onChanged` called 0 times, no "Local settings saved". The window is
small (one 60 s tick during the save) but real.
Fix: give refresh and save separate tickets (a refresh must not cancel a save, and a save must
not be dropped by a refresh), or have the refresh path skip while `busy` save is pending and
re-run after. Add a test for tick-during-save.

**I3. HelpTip text overstates what Settings controls do.**
`SettingsScreen.tsx:88`, `:122`.
"Character or party": "the character or party the Today screen and planners use by default".
Only `TodayScreen.tsx` reads `selected_subject`; no planner does (grep over `src`).
"Manual goal identifier": "the goal profile the planner starts from". Planner screens only
read it when the user presses "Apply local planning defaults" (`PlannerScreen.tsx:94,140`,
`PartyPlanning.tsx:88`), exactly what the on-screen footnote says ("Apply them explicitly in
the planner"). The tip implies automatic use, which AGENTS.md treats as a misleading
distinction. Fix: say "the character or party the Today screen shows" and "goal the planner
fills in when you press Apply local planning defaults".

**I4. Horizontal overflow at 320 px and 200 % text on Local diagnostics and Backup and recovery
(regression).**
`apps/desktop/src/screens/dataScreens.css:2-7`, `DiagnosticsPanel.tsx`, `RecoveryPanel.tsx`.
Measured in Chromium (viewport 320x640, root font 200 %): document `scrollWidth` 597 px on
both screens (also 597 at a 400 px viewport); the path inputs are 532 px wide inside a 190 px
`.ui-field`. The Field grid track is sized by the input's intrinsic width, so the
`max-width:100%` rule at `dataScreens.css:7` does not constrain it; the sized rules at lines
2-4 are scoped to `.snapshot-import`, which only Imports and Content have. On origin/main the
same input measured 256 px and fit. Settings, Imports and Content measured 320/320 (no
overflow). Existing e2e does not test these two screens at 320 px, so CI is green.
Fix: make the Field grid `grid-template-columns: minmax(0, 1fr)` in `ui.css` (src/ui is G4's,
so coordinate) or add `width: 100%` plus the same scoped rules for `.ui-field` generally; add an
e2e overflow assertion at 320 px / 200 % for diagnostics and recovery.

### Optional

**O1. Destructive local-submission actions use the default (secondary) variant.**
`LocalSubmissionsPanel.tsx:68-70` ("Withdraw and erase payload", "Revoke local declaration",
"Erase revoked payload"). They erase payloads or revoke irreversibly, like the screens' other
destructive buttons that were made `danger`. Consider `variant="danger"` for those three.

**O2. Handoff misstates the "latent fix" in LocalSubmissionsPanel.**
`docs/handoffs/2026-10-17-g5b.md` says "Load synthetic price declaration" had no `type` and
submitted the form. On origin/main it already had `type="button"`. What actually changed: the
other buttons in that panel (Accept, Reject, Withdraw, Revoke, Erase, Export, First/Next page)
had no `type`, but they sit outside the form, so behaviour is unchanged. `Button` defaulting to
`type="button"` is correct; `Submit locally` keeps `type="submit"`. Correct the handoff text.

**O3. Contrast HelpTip is not exact.** `SettingsScreen.tsx:134`: "High contrast always uses the
black and white palette". `tokens.css:102-125` keeps gold, accent, ember (primary button fill)
and tone colours in high contrast. Say "a black and white palette with high-contrast accents".

**O4. `dirty` never clears when the user types back to the stored value.** `SettingsScreen.tsx:53`.
Such a draft stays "dirty" and later keeps a stale revision (feeds I1). Compare the draft to the
loaded record's settings, or accept and document.

**O5. Help buttons are disabled inside busy fieldsets.** `ImportScreen.tsx` (`fieldset
disabled={busy}`) and `SettingsScreen.tsx:86`: `Field help` triggers sit inside the disabled
fieldset, so a toggletip a person has open or is focused on disappears from the tab order while
an import or save runs. Low impact.

**O6. Test coverage gaps in `SettingsRefresh.test.tsx`.** The two tests are not tautological
(test 1 fails on the old screen: confirmed, `expected_revision` 1 is asserted and the dirty
value must survive). Missing: stale-save rejection (the mock accepts any revision, so only the
argument is checked; the backend CAS itself is covered in Rust), failed save keeps dirty, save
then tick (I2), conflict recovery (I1), and switching `client` while dirty (only the older test
covers the clear). Add these with the I1/I2 fixes.

**O7. Compatibility screen width unverified against baseline.** At 320 px / 200 % the
Compatibility screen measured `scrollWidth` 896 (Local Data "Extraction resources" select is
798 px wide because of its long option text). I did not measure origin/main for this screen, so
I cannot say whether it is a regression; the old inline label/select may have been equally wide.
Cap the select with `max-width:100%` (see I4).

## Checked and found fine

- Refresh fix, other cases: clean draft follows the store (test 2, and e2e); different `client`
  clears `loaded`, `draft`, `dirty` and invalidates older tickets (`:27-33`, `:61`); a failed
  save keeps the draft dirty and shows the error; a successful save clears `dirty` and adopts
  the returned record; the reset path does not exist in this screen; profile/party lists refresh
  in the background while the draft is kept; the fieldset is not disabled on a background tick.
  Remaining problems are I1 and I2.
- `e2e/refresh-tick.spec.ts`: the Settings case really exercises the bug. With origin/main's
  SettingsScreen restored temporarily, the case fails (`Settings keeps unsaved "Manual goal
  identifier"` red, 5.5 s) and `SettingsRefresh.test.tsx` test 1 fails; restored afterwards. The
  tick is proven by the font-size reapply poll. The `fixme` removal is legitimate.
- `e2e/today-settings.spec.ts`: Tab from the installation path now lands on the Help trigger
  (named "Help") before the export input. That is a real markup change (Field puts the HelpTip
  after the label, before the control) and the assertion still checks focus order; it is
  strengthened rather than weakened.
- Accessible names, roles, headings: Settings h2/h3, Content h2 with h3s, the eligibility panel
  (level 3, same name "Local content eligibility"), Compatibility h2 with Local Data h3,
  Diagnostics h3, Recovery h2 are unchanged in level and name; sections still carry
  `aria-labelledby`. The `section.snapshot-import` became a `div` wrapping a Panel section, with
  the same region name. Axe e2e passes with an empty allowlist.
- Button variants: revoke and restore are `danger`; primary only on form main actions.
  Rollback "Restore previous revision" is correctly not `danger`.
- Unknown/stale/restricted/false/zero: unchanged text and values; `budget_ms` zero is still
  rendered as `0` and the tip says a zero budget is real; "unknown"/"unverified" strings in
  Diagnostics, Local Data and Compatibility are untouched.
- Other HelpTip texts checked against code and found accurate: stopping service, export path
  and format, SavedVariables global/key, restriction reason (released quarantine records
  `operator_review`, `ContentDispositionPanel.tsx:12`), extraction resources ("one worker"
  matches the panel text), diagnostics and backup path tips, selected profile

- Removed high-contrast block in `settings.css`: covered by `tokens.css:102` (palette) and
  `base.css:105-111` (buttons, inputs, selects, fieldsets); the Settings text, surfaces and
  `.ui-panel` also get high-contrast rules in `ui.css:137-145`. The `border: 2px` on native
  inputs is now 1 px from the base rule, a minor visual difference.
- Non-affiliation line remains at `SettingsScreen.tsx:80`.
- Nested Panel layout: Content and Imports have no overflow at 320 px / 200 % (measured
