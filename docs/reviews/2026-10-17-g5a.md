# Review: PR #161, task G5a (play screens on the design system)

Reviewer: Claude Code (Sonnet 5.5) review agent, read-only. Head: origin/feat/g5a-play-screens (bb29aba). Base: origin/main (7370e1a).
Severity scale: plan 21.6 (blocker / important / optional).

Verdict: no blockers. Structure, names, roles, heading outline, variants and test files check out (no test or e2e file is in
the diff). Two HelpTip texts misdescribe behaviour (one states something the code does not do), and HelpTip triggers sit
inside disabled fieldsets in three screens. Fix those before G5b/G6 copy the pattern.

## Findings

### Important

1. **Calibration help says the association is only saved if the quest matches; it is saved regardless** -
   `apps/desktop/src/screens/CalibrationPanel.tsx:256` (help of "Terminal observed quest ID": "The association is only saved if it matches.").
   Scenario: the user types any non-empty quest id and presses "Save association". `SessionCalibrationAnnotation::validate`
   (`crates/core/src/calibration.rs:46-52`) only checks that the id is non-empty and at most 128 bytes, and
   `SqliteStore::set_session_calibration` (`crates/storage/src/calibration.rs:10-30`) checks only that the session exists.
   The match against the session's final `QuestTurnIn` happens later, at comparison time (`calibration.rs:176`), where a
   mismatch excludes the session as `missing_terminal_completion_evidence`. The tip tells the user a wrong id is rejected, so
   they will believe a saved association was verified. The status line after save ("It does not prove route duration;
   revalidation occurs on every comparison") is the accurate statement.
   Fix: "Enter the quest turn-in that ended the session. It is saved as you type it and checked against the recorded
   turn-in only when you compare; a mismatch excludes the session."

2. **Planner budget help understates the constraint** - `apps/desktop/src/screens/PlannerScreen.tsx:721` ("A budget of 0 leaves no time for objectives.").
   Scenario: the planner first prices the route origin to stopping node plus stopping service and rejects the whole request
   when that exceeds the budget (`crates/core/src/planner.rs:185-187`, "Stopping point exceeds session budget"). So a
   budget below the stopping route plus stopping service fails planning outright, not merely "no objectives", and a
   budget of 0 does not exclude objectives that cost 0 ms (`total > budget` is the only cut, `planner.rs:253`). A user who
   enters 5000 ms because it "is enough for one objective" gets an error they were not told about.
   Fix: "Session time limit in milliseconds; 1000 ms is one second. It must cover travel to the stopping node plus stopping
   service, otherwise no plan is produced; each objective must also fit in what remains." The party budget help
   (`PartyPlanning.tsx:569`, "Shared time limit for the whole group in minutes.") and the route budget help
   (`RouteAcquisitionPanel.tsx:825`) omit the same rule; align them.

3. **Party node help invites leaving origin and stopping point unselected, which silently disables calculation** -
   `apps/desktop/src/screens/PartyPlanning.tsx:106` ("Leave it unselected if you do not know it; nothing is guessed."), used for
   "Shared origin" and "Shared stopping point".
   Scenario: `valid` (`PartyPlanning.tsx:88`) requires both `origin` and `stop`, so with either empty "Calculate joint
   estimate" is disabled with no message. The tip reads as if an unknown node is an acceptable input. The Planner's
   equivalent help (`PlannerScreen.tsx:717`) correctly says an unselected origin "blocks planning".
   Fix: "A declared node from the active content. Both the origin and the stopping point are required; nothing is guessed
   for you."

4. **HelpTip triggers sit inside `fieldset disabled`, so they become disabled and unreachable by keyboard** -
   `CalibrationPanel.tsx:241` (`disabled={disabled || busy}`; the screen passes `!native || !profile || busy`, `SessionsScreen.tsx:108`),
   `PartyPlanning.tsx:114` (`disabled={loading}`), `PartyScreen.tsx:107` (`disabled={busy}`).
   Scenario: per the HTML spec every `button` inside a disabled fieldset is disabled (only the first legend's contents are
   exempt). The "?" buttons are `<button>`s, so they cannot take focus or be activated while the fieldset is disabled.
   In the browser demo (not native) the whole calibration fieldset is disabled for the entire visit, so a keyboard user
   cannot read any of its seven tips, although reading them is exactly what explains why the controls are inert. Also, if a
   tip is open and the user starts a request, the trigger is disabled under them and focus is lost. Previously these fields
   had no tips, so this is new behaviour of G5a.
   Fix: render the HelpTip trigger outside the disabled fieldset (move the fieldset `disabled` onto the individual controls,
   or wrap the `Field`s so only the control is disabled), or make HelpTip use `aria-disabled` rather than a native
   disabled state. Add a test that a tip stays focusable inside a disabled fieldset.

### Optional

5. **Planner help sits beside "Clear objective selections" but describes selection, and omits exclusions** -
   `PlannerScreen.tsx:723`. The "?" follows the Clear button, so it reads as help for that button. The text ("Planner
   estimates use only the objectives you tick. Unticked objectives add no assumed reward") is accurate but never says that
   Clear also removes every entered utility/completion/service value and the "Exclude" ticks (`setCandidates([]);setExcluded([])`),
   and it ignores the Exclude checkbox. Fix: move it to the objectives list heading or reword: "Clear removes all
   considered and excluded objectives and their numbers."

6. **Planner profile help understates what changing the profile discards** - `PlannerScreen.tsx:706` says it "discards the current
   estimate"; the effect at `PlannerScreen.tsx:62-66` also clears selected objectives, exclusions, origin and stopping node.
   Fix: "Changing it discards the estimate, the selected objectives and the chosen nodes."

7. **Two Help texts rely on behaviour not stated by the screen** - `GearScreen.tsx:420`/`:421` ("Leave it empty to keep the class
   unknown", "eligibility then stays unconfirmed") match the code (`className ? known : unknown`; empty `{}` map), but the
   manual-model tips (`GearScreen.tsx:418-422`) never say these fields are ignored when an authored model is selected
   (`GearScreen.tsx:405` says the backend resolves weights, proficiency and layout). Fix: add "Ignored while an authored
   model is selected" to the role, weights, class, proficiency and hand tips.

8. **Repeated accessible name "Help" for about 50 triggers** - `ui/HelpTip.tsx` (primitive, not changed here). G5a multiplies it:
   Gear alone has about 16 "Help" buttons in one list. Each is linked to its bubble by `aria-describedby`, but a screen-reader
   user browsing by buttons hears "Help, button" with no field. Fix in the primitive: accept a `label` prop and name the
   button "Help: Budget (ms)" (the visible "?" is `aria-hidden`, so a longer name does not break WCAG 2.5.3). Carried from the
   G4 review (finding 2).

9. **Native `ui-button` buttons remain** - `AtlasScreen.tsx:220` and `RouteInspection.tsx:50` use `className="ui-button ..."` because
   `Button` has no `ref` in its props type (`ui/Button.tsx`, `Omit<ButtonHTMLAttributes, "className">`). Both are justified (roving
   focus needs refs) and only these two exist (`grep "<button"` over the play screens). Fix in a follow-up: add
   `ref?: Ref<HTMLButtonElement>` to `ButtonProps` (React 19 passes it as a prop) and `aria-pressed` styling for the
   route-hop buttons, which currently show no visual difference between pressed and unpressed.

10. **Legacy button rules override `.ui-button` padding** - `src/styles.css:17` (`.map-toolbar button, .pins button { padding: 0.25rem 0.7rem }`,
    specificity 0,1,1) beats `.ui-button` (0,1,0), so the map toolbar and pin buttons are smaller than every other Button.
    Cosmetic; the smaller target is still above 24 px at default size. Fix: scope those rules away or raise `.play-screen .ui-button`.

11. **Nested panels cost horizontal space at 320 px and 200% text (not measured)** - `play.css:5-12`, `ui/ui.css` `.ui-panel`.
    `.play-screen` pads 1rem and each `Panel` pads 1rem per side; Party joint planning is screen > Panel > Panel (6rem of
    padding in total, 192 px at 200% text on a 320 px viewport). The 320 px a11y and reflow specs pass, so nothing overflows,
    but the column is very narrow. Unverified by eye; consider zero padding for a Panel nested in a Panel.

12. **`.saved-plan` and `.marker-panel` class hooks were dropped** - `SavedPlanCard.tsx`, `AtlasScreen.tsx` `MarkerPanel`. No CSS targets
    `.marker-panel`; `.saved-plan` is only in `settings.css:4` (`overflow-wrap`, `min-width`), now covered by `.ui-panel` and
    `.play-screen`. No visible effect; noted so the dead selector in settings.css is removed rather than relied upon.

13. **Multiple `primary` buttons per screen** - Gear has "Compare gear" and (via the panel) "Preview reserved route"; Calibration has
    "Save association" (primary) next to "Compare retained sessions" (secondary), although saving is the lesser-used action.
    Not wrong, but the primary emphasis is diluted. Consider making "Compare retained sessions" the primary there.

## Verified as correct (no finding)

  `core/gear/acquisition.rs:209-213` reports a field as unavailable), independent attempts (`ProbabilityModel::DeclaredOnly`

  `--text on --surface` is declared (4.5). The sheet is 90 % `--surface` over the backdrop, so the effective background
  moves a few percent from the tested one; `--text` has large headroom (about 12:1) so this does not threaten 4.5:1.
  High-contrast and forced-colours rules replace the translucent sheet with `--surface`/`Canvas`. The `--tone-warn` note
  border is a non-text 1 px edge with no declared 3:1 pair (the handoff admits it); the 0.3rem left edge and the text
  carry the meaning.
- Duplicate ids: HelpTip and Field use `useId`; no static ids were added. Panel names do not collide within a screen.

## Resolution (2026-10-17)

behaviour (saved as entered, excluded at comparison on mismatch; budget must cover
travel plus stopping service; origin and stopping point both required). Important 4:
HelpTip's trigger is now a focusable `span role="button"` so a surrounding
`fieldset disabled` cannot disable help (new unit test, Enter and Space). Optional 5
and 6 (Clear tip, profile tip scope) were folded in for Clear; 6, 7 and 8-13 are
carried to the 0.9.2 TODO (HelpTip label prop, Button ref, nested panel width,
multiple primary buttons). Rechecked: typecheck, lint, 337 unit tests, build,
check-dist, Playwright 158 passed / 1 skipped. Screen-reader behaviour unverified.
