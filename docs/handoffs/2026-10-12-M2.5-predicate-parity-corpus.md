## Goal and scope
Plan section 6.7 says Lua and Rust evaluation semantics need parity tests; sharing
JSON names alone is not enough. This package ships only the Rust-anchored half:
a fixture corpus whose expected values come from the Rust evaluator, and a
data-driven Rust test that proves the corpus and the evaluator agree. The later
Lua evaluator (P12b, wave 2, after the addon skeleton merges) consumes the same
corpus unchanged. No `.lua` file, addon file, CI file, `crates/core/src` file or
dependency was touched (scope override of the overlap judge).

## Implemented
- `fixtures/predicates/v1/`: `manifest.json`, `README.md` (case-file format,
  generators, lua_only, regeneration, notes for the Lua half) and ten case files
  with shared named snapshots and parties: operators, truth-tables, unavailable,
  missing-history, party, freshness, limits, context-mismatch, equipment, inputs.
- 192 cases: 189 executed by Rust, 3 `lua_only` (counted and skipped). That is
  more than the "about 40-60" in the task text, because the acceptance list names
  many distinct behaviors (every operator, four unavailable statuses, freshness
  paths, exact limit boundaries, rejected inputs, ordering traps). Cases are
  small and share snapshots; `inputs.json` is the largest file.
- Named synthetic CASE versions in `case_ref`: CASE-001 (missing-history.json),
  CASE-002 (party.json), CASE-005/011/015 (context-mismatch.json, party.json),
  CASE-010 (unavailable.json).
- `crates/core/tests/predicate_parity.rs`: one data-driven test. It decodes
  `Predicate`, `CharacterSnapshot` and `PartySnapshot` with the existing serde
  types, builds `FreshnessContext`, `StalePolicy` and `RuleLimits::new` from a
  test-local spec (those types have no `Deserialize`; nothing was added to core),
  calls `evaluate`, and compares the serialized `EvaluationResult` (truth, steps,
  reasons and warnings in order), `{"error": CODE}` or `{"rejected": true}`.
  Error messages are never compared.
- Test guards: every `*.json` in the corpus directory must be in the manifest and
  vice versa; declared per-file and total counts must match; case ids are unique;
  each `expected` is well formed; lua_only cases must expect `{"rejected": true}`;
  all 14 operators, all four unavailable statuses, all three truth values,
  BUILD_MISMATCH, INVALID_INPUT, rejected inputs and the six CASE references must
  occur. A mutation check (changing one expected step count; adding a stray
  JSON file) made the test fail as intended.
- Generators (`nest` and `wide`) build depth and width cases from a declarative
  spec so no fixture file needs more than a few JSON levels (the addon decoder
  limit is 32). `PREDICATE_PARITY_DUMP=<path>` writes the actual outcomes of all
  executed cases for regeneration; it writes nothing otherwise.

## Decisions
- No ADR. Design notes live here and in the corpus README.
- The `PredicateNode` enum has 14 operators, not 15 as the task text said; the
  test pins the 14.
- Expectations come from Rust. Authoring used a throwaway script outside the
  repository (not committed) that stated the intended truth, error or rejection
  and, for selected cases, the intended step count, and checked each against the
  dumped Rust result before writing `expected`; every intended outcome matched on
  the first dump, so no Rust behavior was in conflict with intent.
- Party mixed-namespace shapes are split by where Rust rejects them: a party
  whose participants disagree with its own context fails to decode (rejected); a
  wholly reference-namespace party used with a demo snapshot decodes and gives
  BUILD_MISMATCH at evaluation.
- `lua_only` expectation is `{"rejected": true}` for all three cases (duplicate
  key in an ignored member, 33-level nesting in an ignored member, 32 KiB
  budget). A scratch test (deleted) confirmed Rust accepts all three inputs, so
  they cannot be exercised here; they remain unverified until the Lua decoder exists.

## Limitations
- Parity with a Lua evaluator is not yet checked; nothing in CI exercises the
  Lua side. The three lua_only cases and the decoder-level number and string
  traps are documented but unverified in any second runtime.
- `ClockReversed` and `AgeOutOfRange` freshness outcomes both surface as the same
  `clock_uncertain` reason, so the corpus can only distinguish them from Fresh
  and Stale, not from each other.
- `evaluate_rule` and rule expiry, plan import, HUD and gear scoring are not
  covered (wave 2).
- Corpus size (192 cases, about 230 KB) exceeds the suggested range.

## Review focus
- Rust behavior recorded as-is, worth a deliberate look: `known` is false for a
  stale value under the reject policy (`fresh-stale-known-reject`); an observed
  empty equipment slot is false while an unrecorded slot is unknown; a variant
  that is unknown still lets a definite modifier mismatch return false
  (`equip-variant-unknown-then-mismatch`); a modifier-constraint set that is
  empty never consults the modifiers observation, even if it is unknown.
- Step accounting is fragile for any second implementation: one step each in
  `node`, `field`, `usable`, the equipment slot lookup, each modifier key and each
  scanned party participant (`limit-steps-*`, `party-*`, `equip-modifier-order-*`).
- Bytewise key order: `equip-modifier-order-utf8-not-utf16` separates UTF-8 from
  UTF-16 order; `equip-modifier-order-missing-before-mismatch` separates
  uppercase-first order.
- Number lexemes: `1.0`, `-0.0`, `22.0` (rejected for integers), `1e400`, and the
  2^53-1 boundary in `inputs.json` and `equipment.json`.
- `fresh-age-out-of-range` uses values at +/-(2^53-1); a double-based
  implementation must keep the subtraction exact or compare before subtracting.
- The corpus has its own manifest format: P2's `validate-fixtures` must keep to
  its explicit manifest list and not glob `fixtures/**` (ADR 0003).
