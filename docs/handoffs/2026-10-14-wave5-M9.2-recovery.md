## Implementation and decisions

Storage recognizes only exact repository-created historical schemas1–8 and exact
migration histories before querying application tables. Every copied column/name
comes from trusted migrations. Read-only source data is bounded (512MiB including
sidecars,1million rows,32MiB per row plus existing feature bounds), copied into a
fresh trusted schema, migrated and validated. Imported SQL is never executed.
Integrity, foreign keys, all historical snapshot metadata/observations/hashes,
full profile/context/fixture pointers, content manifests/sources/conflicts,
preferences, sessions/derived analytics/hashes, annotations, reminders and local
proposal storage are checked. Application inspection additionally validates typed
proposal requests. Future migration tables must register a recovery copier; the
validator refuses rather than silently dropping their data.

DatabaseHost keeps a ready application or actionable startup failure; native
startup checks run on a background worker. Its read lease covers the entire
ordinary application call, so explicit restore waits for in-flight work. Watchers
stop/join before the final healthy SQLite online backup and connection closure.
Source previews produce staged identities/hashes. Changed previews or tampered,
symlinked/nonregular/oversized candidates cannot cross the destructive boundary.
Original DB/WAL/SHM files and the healthy consistent backup remain in a unique
sibling directory. Injected installation failure rolls original files back.

A persisted pending marker guards interruption; startup never silently creates an
empty database during incomplete replacement. Existing bounded regular markers
remain byte-for-byte unchanged throughout failed retries, including empty,
nonUTF8 and truncated content. A successful explicit retry clears them. Cleanup
failure is an explicit receipt/status/UI warning; next startup remains guarded.
Power-loss atomicity and multi-process restore are not claimed. Other application
instances must be closed. Normal SQLite WAL readers may manage SHM locks; corrupt
headers are rejected before SQLite can alter their sidecars.

Five typed native/client commands expose status, integrity check, create-new
backup, inspect and staged restore. All prior native commands keep their existing
names/arguments and execute through the application lease. The native recovery
panel is available on startup failure and ordinary navigation, requires explicit
replacement acknowledgment and retains the result/warnings after restoration.
Browser demo file operations are refused. See DATABASE_RECOVERY.md for user steps.
No exchange/dataset schema, edition identity, game action or addon bridge changes.
