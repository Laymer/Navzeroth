## Goal and scope
A minimal diagnostic addon that records build and capability results without
collecting restricted or personal data and without compatibility workarounds
(plan M0.3, section 23.1 item 3), plus the Lua tooling to test it without a client:
a dev-only Lua 5.1 harness crate, luacheck configuration and one CI job, a
machine-readable capability template, and install, SavedVariables and runtime
documents. Out of scope and not implemented: observation adapters (M2.1), the ANAV1
export (M2.2, normative in the ingest package), the predicate port (wave 2), the HUD,
plan import, party sync, localization.

## Implemented
- `addons/AzerothNavigator/`: TOC (`## Interface: 16001` with an UNVERIFIED comment
  and `## X-Interface-Status: UNVERIFIED`, `## SavedVariables: AzerothNavigatorDB`),
  `Core/` (canonical casing) with Bootstrap, Version, Json (bounded deterministic
  encoder), Capabilities (probe), Export, Settings, and `Diagnostics.lua` (the only
  file that binds to the client environment, through an injected `_G`).
- Probe: 16 capabilities with existence checks on assumed mainline-style names and
  exactly one call, `GetBuildInfo`, inside `pcall`. Emits only `untested` and `failed`
  from the BUILD_CAPABILITIES.md vocabulary; no shim for missing APIs; no personal
  data read.
- Export: package-local JSON `{"format":"anav-diagnostic",...}` (not ANAV1, not a
  contract kind), capped at 12288 bytes, rejected whole on any bound violation.
- `.luacheckrc` (`std = "lua51"`, line length 100, empty `read_globals` because all
  client access goes through the injected table, `globals` limited to the two
  declared names).
- `crates/lua-harness` (`azeroth-lua-harness`): vendored Lua 5.1.5 via mlua 0.12.2
  (exact pin, `lua51` + `vendored`), restricted stdlib, whitelisted environment,
  strict-global mode, memory and instruction budgets, TOC parser, forbidden-name
  source scanner; 57 tests.
- `docs/compatibility/capability-observations.template.json` (section 22.4 fields,
  all rows `untested`), `ADDON_INSTALL.md`, `ADDON_SAVEDVARIABLES.md`,
  `LUA_RUNTIME_DIFFERENCES.md`; `fixtures/addon/` (own manifest, three golden
  exports plus a synthetic SavedVariables layout sample).
- `.github/workflows/ci.yml`: one new job "Lua static checks" (see Decisions).
- `Cargo.toml`: one members line. `Cargo.lock`: additions only (mlua, mlua-sys,
  lua-src, luajit-src, which, bstr, either, azeroth-lua-harness; no existing entry
  changed).

## Decisions
- No numbered ADR (ADR 0003 rule). Design notes live in this handoff and in the three
  compatibility documents; the integration docs PR may promote them.
- Policy note on the embedded Lua VM: plan section 7.2 forbids executing imported
  SavedVariables with a Lua interpreter or embedded VM. The harness runs only this
  repository's addon sources and snippets written in its own tests; its crate docs
  and LUA_RUNTIME_DIFFERENCES.md state it never loads SavedVariables or imported data,
  and it is a dev-only crate that no other crate depends on. The desktop importer
  (M2.3) must parse the file as data. A reviewer may still want this restated in the
  integration ADR.
- The probe never writes `verified available`, `verified unavailable` or
  `restricted`: a stub or a real client cannot tell the probe whether its environment
  is trustworthy, so only an operator with recorded conditions can. A missing API is
  `untested` + `api_missing`; a raising call is `failed`.
- `build.edition` is `wow_forever` with `edition_basis: assumed_target`; the edition
  is not readable by the probe. Mapping to `BuildKey` is left to M2.1.
- Integer-only JSON, sorted keys, empty table is `[]`: avoids Lua/serde float
  formatting differences and makes golden files byte-comparable.
- `luacheck` runs through `lunarmodules/luacheck@2445a9dd3859655646bd6eb848459f2b46b4a3e3`
  (tag v0.26.1, resolved with `git ls-remote`; the action file at that SHA runs the
  `ghcr.io/lunarmodules/luacheck:v0.26.1` image, whose manifest returned HTTP 200).
- `Core/` is the canonical directory casing for the later predicate port.

## Limitations
- UNVERIFIED until a client check: interface 16001, the SavedVariables directive and
  file location, every API name in the catalogue, `CreateFrame`/`SlashCmdList`
  behavior, the event names `ADDON_LOADED` and `PLAYER_LOGIN`, when the client writes
  SavedVariables, the AddOns path, and the redaction of real client error text (tested
  with synthetic patterns only). No CASE scenario was run live; CASE-010 is
  IMPLEMENTED_UNVERIFIED (synthetic).
- The Windows MSVC build of vendored Lua 5.1 and its build time against the 20-minute
  Rust job limit are unverified locally. The new Lua job is not a required check, so a
  red luacheck run could merge unnoticed; call it out in the PR.
- `fixtures/addon/savedvariables-sample.synthetic.lua` is a synthesized layout, not a
  captured file; P2's parser must not treat it as evidence of the client's format.
- The harness approximates the WoW sandbox (see LUA_RUNTIME_DIFFERENCES.md); redaction
  is best effort and cannot recognize a bare name, so it is applied only to the errors
  of the single call and lookups the probe makes.
- `BUILD_CAPABILITIES.md`, STATUS, README, DOMAIN and SOURCES were intentionally not
  edited; the integration docs PR reconciles them.

## Review focus
- The probe's status policy (only `untested`/`failed`) and the `api_missing` wording.
- `Json.lua`: depth counting (top-level container is depth 1), node and element caps,
  the metatable rejection, and `%.0f` number formatting.
- Whether `.luacheckrc` with an empty `read_globals` and `globals` limited to two names
  is acceptable given that client access goes through the injected `_G`.
- The sandbox whitelist in `crates/lua-harness/src/lib.rs` and the forbidden-name list.
- The CI job: pinned action SHA, image tag, and that it is not required.
- Overlap with the ingest package: global name and key layout in
  ADDON_SAVEDVARIABLES.md are what its parameterized extractor targets in wave 2.
