## Question

The fresh 70450 extraction (catalog `7cd6eeed…1519e`, main `5b346d6`, preset max)
reported 106 of 1,346 tables as `invalid_corrupt` / `archive_verification_failed`,
including Item (841626), ItemSparse (1572924) and Map (1349477).

## Root cause

None of the 106 is corrupt. All 106 are **partially encrypted** DB2 files: the
leading BLTE frames are plaintext and verify, and the trailing frames are BLTE
mode `E` (encrypted) with a key that is not available locally.

CascLib's `CascReadFile` does not fail in that case. Its frame-cached reader
stops at the first frame it cannot decode, records that frame's error
(`ERROR_FILE_ENCRYPTED`) as the last error, and returns **success with a short
byte count**. The wrapper (`native/offline.cpp` `nav_casc_read`) turned every
short count into status 4, which Rust classified as `ReadFailure::Invalid` →
`invalid_corrupt` / `archive_verification_failed`. The real cause was dropped.

This is a classification bug, not a reader bug a strict read can fix: the open
flags, locale (enUS mask 2, `CASC_LOCALE_ALL_WOW` per file), product and strict
checksums were correct, and the encrypted frames genuinely cannot be decoded
without keys, which the project does not acquire.

## Changed

- `crates/local-data/native/offline.cpp`: `nav_casc_read` clears the last error,
  reports bytes produced through a new `done` output, and on a short count returns
  the status of the error CascLib recorded. A short count with no recorded error
  is its own status 8. `ERROR_HANDLE_EOF` / `ERROR_FILE_INCOMPLETE` map to a new
  status 7. Strict checksums stay on; no zero-fill flag, no key interface.
- `crates/local-data/src/native.rs`: `ReadFailure` gains `EncryptedFrames`
  (encrypted frame after produced frames), `Truncated` (status 7) and `ShortRead`
  (status 8). `classify_read` maps status + produced count. The partial buffer
  is dropped. Unit tests cover every status and the short-read cases.
- `crates/local-data/src/extraction.rs`: the disposition mapping is now
  `read_failure_disposition` with a unit test that requires distinct reasons and
  checks that encryption and incomplete or unexplained reads never map to
  `invalid_corrupt`. New reasons: `unavailable_encrypted_frames`,
  `archive_span_incomplete` (`not_locally_present`), `archive_short_read_unexplained`
  (`unavailable_encrypted`). Existing reasons keep their meaning.
- `docs/data/LOCAL_EXTRACTION.md`: "Archive read failures" table with each
  cause, disposition and reason.

The extractor profile hash changes (it covers the wrapper and Rust sources), so
new catalogs carry a new `extractor_profile_sha256`. Existing catalogs are still
valid but keep the old misleading reason. Re-extract to get the corrected reasons.

## Can Item / ItemSparse / Map be read strictly now?

No, not as whole logical files. They are now reported correctly as encrypted gaps,
not corruption. Their plaintext frames verify, and the encrypted frames fall
exactly in DB2 sections whose tact-key lookup is non-zero. The decoder
(`tables.rs`) already skips those sections without reading them and reports
`encrypted_section_records` gaps. A **frame-aware strict partial read** could
therefore decode their plaintext sections without keys, zero-fill or recovery:
read and MD5-verify each plaintext frame, record each encrypted frame's range as
explicitly unavailable, and have the decoder refuse any access that touches an
unavailable range (instead of a zero-filled buffer). That is a design and policy
decision (localdata.md: "missing and encrypted local content remain gaps"; no
zero-fill). It is not implemented here.
