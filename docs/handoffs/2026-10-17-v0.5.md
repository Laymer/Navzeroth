# V0.5: startup database-check race in the desktop app

Owner and sole writer: Claude Code (Opus 5.5); claim [2026-10-17-v0.5](../claims/2026-10-17-v0.5.md).
Baseline main `4decacc`. Branch `fix/V0.5-startup-check-race`.

## What failed

The hosted "Native WebView2 smoke over CDP" failed on PR #170 head `73e2286`
(run 39038169018, job 117412247534): 3 of 25 smoke checks, with "Navigation did not
reach 14 buttons; alerts=[Error PROVIDER_UNAVAILABLE: Database initialization is
still checking (you can retry)]". PR #170 changes no desktop or `crates/app` file,
and the same smoke passed on main `4decacc` and on PRs #168 and #169.

## Cause

At startup `App` calls `getAppStatus`. While the backend's startup integrity check
runs, every call returns `PROVIDER_UNAVAILABLE` (retryable), so `App` enters its
error state and shows `RecoveryPanel`. The panel polls the database status and
reloads the app (`onChecked`) only if it saw `checking` itself. When the check
finishes between the failed `getAppStatus` and the panel's first poll, the first
poll sees `ready` and the panel doesn't reload. The app stays on the recovery view
until the 60-second freshness refresh reloads it, long after the smoke's 20-second
wait for navigation. A slow runner (or a slow user disk) hits this window.

## Fix

`App` passes `awaitingStartup` (load failed with retryable `PROVIDER_UNAVAILABLE`)
to `RecoveryPanel`, which then also reloads on its first `ready` poll. Recovery
required still doesn't reload; a ready database with no waiting load doesn't either.

## Checks (actual, WSL2)

- New tests: `RecoveryPanel` (a check finished before the first poll reloads; no
  reload when nothing waits; no reload for recovery required) and `App` (the full
  smoke sequence reaches the empty-state view after one retry). Both new
  race tests **fail without the fix** (verified by stashing the source change) and
  pass with it.
- `pnpm typecheck`, `pnpm lint`: pass. `pnpm test:unit`: 44 files, 376 tests passed.
- Native WebView2 behaviour: verified only by the hosted smoke on this PR.

## Independent review

A shell-capable reviewer in an isolated worktree found no blockers and no
important findings. It verified the diagnosis against `crates/app/src/recovery.rs`
(the only retryable `PROVIDER_UNAVAILABLE` is the startup-check path), confirmed
that no reload loop is possible, and re-ran the tests with the fix reverted:
exactly the two race tests failed. Recorded optional items: the diagnostics screen
doesn't mount the panel during an error load (pre-existing; it still recovers on
the 60-second refresh), and there's no test for the checking-then-ready order with
`awaitingStartup` set.
