## Delivered behavior and decisions

Registered list_parties, get_party, save_party and delete_party as explicit Tauri
commands. Party IDs deserialize through the checked core type; all service calls
run on the existing blocking worker boundary. TypeScript DTOs/client mirror the
application service. Browser demo returns an empty party list and refuses writes.

Party navigation supports named local configuration, editing membership and scoped
removal. Profile choices show full build/interface/namespace/synthetic context;
backend validation remains authoritative. New-party name collisions require
selecting the existing party to edit. Membership requires 1–40 selected profiles;
the store also caps total parties. Missing/deleted member identities stay visible
and can be explicitly removed from an edited party.

Each participant displays their own imported snapshot, backend-computed capture
age/freshness, level, role and quest acceptance/completion/turn-in/objectives.
False and all observation status labels stay distinct. Empty quest records do
not imply complete history. Missing captures are explicit. Synthetic snapshots
are labelled, and stale/uncertain captures explain that progress may have changed.

App minute refresh and watcher imports refresh the open party view. Selection and
unsaved membership survive refresh. Superseded reads are ignored, failed edits
retain saved membership and draft state, and controls serialize mutations. Removing
a party preserves all character snapshots and preferences. Joint eligibility and
planning are explicitly marked unavailable pending the next integration task.
