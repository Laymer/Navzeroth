## Delivered behavior and decisions

SQLite v3 adds party_profiles and ordered party_participants. Save is an immediate
transaction with validation before replacement. Limits are 128 local parties
and 1–40 distinct characters per party. Members must have identical edition,
build, interface, namespace and fixture mode. Saving requires existing profiles;
profiles created by manual preferences may legitimately have no current snapshot.

Stored membership retains the exact typed ProfileKey. The optional database
profile reference uses ON DELETE SET NULL; the identity survives deletion and
resolves newly imported state of that exact identity again. Reads validate stored
keys and party invariants. Deleting a party cascades membership only. Saving a
party never modifies character observations, preferences or import ordering.

SnapshotApplication exposes save_party, party_ids, party and delete_party.
StoredParty contains separately identified participants, each with an optional
StoredSnapshot and independently recomputed freshness. Missing captures serialize
as null; known/unknown/restricted/false/zero observations remain in the original
validated character envelope. Reads hold the service mutex for the whole view.

Regressions cover reopen, profile deletion/reimport, missing snapshots, individual
freshness/progress, older import preservation, atomic failed replacement, duplicate
characters, incompatible contexts, count limits, corrupted membership, deletion
scope and populated v1/v2 migration preservation. The v2 check also verifies hash

existing hard-coded v2 assertion and a context mismatch in the new migration test
setup; both were corrected before the passing run. Review inspected bounds,
transactions, identity isolation, deletion scope and stored-data validation.

## Limitations and next task

This is the local manual party storage/application foundation of M7.3; the full
manual planning milestone remains in progress. Tauri commands and the Party screen
are not wired yet. PartySnapshot transport imports remain explicitly rejected by
the character import workflow. No game synchronization or proposal acceptance was
implemented. Real content, live client checks, native interaction and packaging
remain unverified. No hosted CI or Windows checks were run for this change.

Next task: wire explicit Party commands and UI to these application methods and
show per-participant missing/stale state, then consume the existing pure party
eligibility API. Preserve character import semantics and require recorded build
evidence before any addon messaging. The unrelated .claude/ directory is preserved.
