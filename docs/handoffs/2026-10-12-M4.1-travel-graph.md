## Goal and scope
Wave-1 package P3 of ADR 0003 (early start on synthetic data, plan section 17
M4 allows synthetic planner tests early): a pure travel-graph shortest-path
module that the later planner (M4.3) can call. Plan sections 9.1, 9.2 and

Cargo change.

## Implemented
- `crates/core/src/travel.rs` (new), plus one line `pub mod travel;` in
  `crates/core/src/lib.rs` (between `predicate` and `types`; `sources` does
  not exist on this base).
- `shortest_route(nodes, edges, origin, target, &EvaluationContext, &RouteOptions) -> Result<RouteSearch>`.
  `RouteSearch { outcome, exclusions }`; `RouteOutcome::{Complete{route}, Incomplete{target, reached, reachable}}`;
  `Route { start, hops, total_ms }` with `end()`, `is_estimate()` and
  `to_travel_segments() -> Vec<TravelSegment>`; `RouteHop` keeps each edge's
  observations (expected, wait, range, consumes_resource, cooldown) unchanged.
- Dijkstra on `std::collections::BinaryHeap`. The label is
  `(total ms, hops, Vec<EdgeId>)`: lowest cost, then fewer hops, then the
  lexicographically smallest edge-id sequence. The label is totally ordered
  and strictly grows along any extension, so settled labels are optimal with
  zero-cost edges and cycles (settled set; nothing is re-expanded).
- Edge cost = expected + wait + caller service time, with checked addition
  capped at `MAX_SAFE_INTEGER`; overflow of an edge or of a route total is an
  `InvalidInput` error. `wait_ms` Known adds its value, NotApplicable adds 0,
  any other status excludes the edge; `expected_ms` not Known excludes it.
- `TravelExclusion` (local, `#[serde(tag = "code", rename_all = "snake_case")]`):
  `map_mismatch`, `temporarily_unavailable`, `unverified`,
  `requirement_unavailable{status}`, `requirement_not_met`,
  `requirement_unknown{issues: Vec<EvaluationIssue>}`, `cost_unknown{term}`,
  `stateful_not_verified`, `stateful_availability_unknown{consumes_resource, cooldown}`,
  `stateful_not_final_hop`. One reason per edge, chosen in the order map,
  status, requirement, cost, stateful. Exclusions are sorted by edge id and
  carry ids and codes only.
- Eligibility: status Verified or Estimated; requirement NotApplicable, or a
  Known predicate whose `evaluate()` truth is `True`. `False` and `Unknown`
  stay separate reasons; Unknown carries the `EvaluationIssue` list. An `Err`
  from `evaluate()` propagates.
- Context and bounds: every node position, edge and the snapshot must share a
  `DataContext` (`BuildMismatch` otherwise, demo and reference never mix).
  More than 1024 nodes or edges, duplicate ids, a dangling node reference, an
  unknown origin/target and an unknown service-time key are `InvalidInput`.
  An endpoint `NodeRef.map` that disagrees with the node's `Position.map`
  excludes that edge (`map_mismatch`); no cross-map comparison or geometry is used.
- Stateful edges (mode Return or Teleport, `consumes_resource` Known(true), or
  `cooldown_ms` Known(>0)) are never relaxed inside Dijkstra. After the
  search, at most one may close the route as its final hop, only when
  Verified, requirement-eligible, and with `consumes_resource` and
  `cooldown_ms` both Known. Candidates (the plain route and each such closing
  hop) are compared with the same label order. A stateful edge that does not
  end at the target is reported as `stateful_not_final_hop`.
- Incomplete routes report `reached` (the known segment ending at the settled
  node with the highest cost, ties by node id) and the sorted `reachable` set;
  nothing joins the gap.
- Tests: `crates/core/tests/travel.rs`, 20 tests, including CASE-004
  (`case_004_unknown_flight_path_not_assumed`), locked flight path, directed
  edge, map/floor boundary, disconnected graph, unavailable/unverified/
  estimated transport, return-at-most-once, unknown return availability,
  24-permutation determinism plus reversed node order, BuildMismatch (build
  and namespace, edge and node), cost overflow, zero-cost cycles, error
  propagation of an evaluation step-limit error, and `RoutePlan` validation of
  the produced segments.

## Decisions
- petgraph (plan section 5.1) is not used; std `BinaryHeap` instead. petgraph's
  `dijkstra` returns costs only (no predecessors) and offers no control over
  tie-breaking, so the deterministic tie-breaks and exclusion explanations
  would need custom code regardless, and a new dependency would change
  `Cargo.toml` and `Cargo.lock`, which are shared hotspots in wave 1. This is
  recorded here and not as a numbered ADR, per ADR 0003.
- Service time has no contract field. It is a caller-supplied
  `RouteOptions.service_ms: BTreeMap<EdgeId, Millis>`, charged each time that
  edge is used, default 0. Per-edge (not per-node) keys avoid charging
  boarding time to walkers that merely pass a service node.
- Segment `expected_ms` is the edge's own travel duration so that
  `RoutePlan`'s range check holds; waits and service time are in
  `Route::total_ms` and in each `RouteHop`.
- Unknown `consumes_resource` / `cooldown_ms` on an ordinary-mode edge (walking,
  flight, boat, tram) that is not otherwise stateful does not make it stateful
  (otherwise sparse data could route nothing); the hop keeps the unknown
  observations so callers can see them. Return/Teleport modes require both known.
- A stateful edge with requirement NotApplicable is eligible; cooldown
  readiness has no observation channel, so it can only be expressed through the
  requirement predicate.
- Return/teleport edges use their explicit `from` node. No "from anywhere"
  edge is invented.
- Walking edges with unknown wait are excluded like any other mode (never
  assumed 0).

## Limitations
- The Predicate language has no "flight path learned" field, so CASE-004 is
  expressed through an unknown requirement observation, a missing snapshot
  record (Truth::Unknown) or `EdgeStatus::Unverified`. A taxi-node field needs
  a versioned contract change after the wave-1 freeze.
- No contract field for service time, a learned taxi-node set or
  reference-versus-unlocked edge separation (M6.4); the last waits for wave 2.
- Cooldown readiness and consumable possession are not observable here; a
  stateful edge is usable when its requirement passes and its resource state is
  Known. Only a verified edge is reserved, and only as the final hop.
- `reached` in an incomplete outcome is the highest-cost settled node, not a
  claim of being nearer the target (no geometry or heuristic by design).
- Declared expected waits only; no time-dependent schedules (plan section 9.2).
- The fixed data are synthetic; no real routes, zones or durations are
  included. Nothing is labelled live.
- Not wired to any app, CLI or storage code; no `fixtures/travel/` added.
- The review record was committed after PR 10 had merged into main, so it
  reaches main only through a follow-up documentation PR.

## Review focus
- The total order of the Dijkstra label and the claim that it keeps
  optimal substructure (cost, then hops, then edge-id sequence), especially
  with zero-cost edges.
- Whether excluding a stateful edge that does not end at the target
  (`stateful_not_final_hop`) is the right user-visible explanation.
- The one-reason-per-edge ordering (requirement before cost) and whether the
  planner wants every failing reason instead.
- Treating unknown `consumes_resource`/`cooldown_ms` on ordinary modes as
  non-stateful (see Decisions).
