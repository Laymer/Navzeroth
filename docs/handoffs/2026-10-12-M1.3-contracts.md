## Goal and scope
Versioned exchange contracts built on the M1.2 validated domain types: bounded
validation, generated JSON Schema and TypeScript types, synthetic fixtures and CI
drift detection. Out of scope: UI, transport (ANAV1 grammar, M2), storage (M1.7),
route search, gear scoring and Lua parity.

## Owner decisions (asked this session)
- Generation: schemars, then JSON Schema 2020-12, then json-schema-to-typescript.
  Checks use Ajv and tsc.
- `demo` namespace requires `fixture: true`. A fixture may use the `reference`
  namespace.
- Timestamps stay integer UTC milliseconds. This deliberately differs from the
  illustrative RFC 3339 string in plan section 6.4.
- Unknown top-level envelope members are retained as bounded extensions. Unknown
  nested members are dropped, as in M1.2.

## Implemented
- `crates/core/src/contract/`: a common envelope (format, kind, schema version,
  fixture, producer, game, namespace, provenance, dependencies, payload,
  extensions) for six kinds: `character_snapshot`, `party_snapshot`,
  `route_plan`, `evidence_bundle`, `reference_dataset` and
  `gear_recommendations`. Pure `decode_envelope`/`decode_any` check, in order:
  size, header, nesting depth for addon-facing kinds, typed structure, then
  semantic rules.
- Semantic rules:
  - payload contexts equal the envelope build and namespace (`BUILD_MISMATCH`);
  - fixture, namespace and provenance agree, including nested observation
    sources;
  - dependencies equal the payload's own values;
  - plans keep the section 7.1 limits: 100 steps, 8 alternatives, rule depth 12;
  - evidence bundles and reference datasets resolve local references
    (`DATASET_INCOMPLETE`);
  - gear sets are consistent.
- RoutePlan completes section 6.5: capability assumptions, revalidation
  triggers, per-step evidence and estimates, and travel ranges.
- JSON Schema derivations for all domain and contract types, with explicit
  schemas for custom serde representations. The CLI command `export-schemas`
  writes `schemas/v1/exchange.schema.json`; `pnpm contracts:types` writes
  `schemas/v1/exchange.ts`.
- 52 synthetic fixtures plus a manifest: 9 valid, 16 schema_invalid and 27
  semantic_invalid, each negative case with its expected error code.
- Rust tests: manifest outcomes, round trips, limits, extensions, schema drift.
- Node check: tsc strict type check with `@ts-expect-error` contract cases, Ajv
  outcomes for every fixture, and exhaustive TypeScript narrowing of the valid
  fixtures.
- CI: the pnpm jobs regenerate the TypeScript, fail on any diff and run the
  contract checks. The Rust jobs catch schema drift through `cargo test`.
  `.gitattributes` pins LF line endings.
- Documentation: `schemas/v1/README.md` (fields, absent-field meanings, limits,
  error codes, resolution boundaries, schema gaps, compatibility),
  `docs/DOMAIN.md`, `README.md`, and the review record
  `docs/reviews/2026-10-12-M1.3.md`.

compiled by tsc into `node_modules/.cache/contract-check` and run as
JavaScript, so it does not depend on Node's TypeScript support.

## Limitations and remaining risks
- Hosted Linux/Windows CI has not run yet; check the draft PR. Windows TS7
  binaries and LF handling have only been reasoned about, not executed.
- Lua decoding and evaluation parity are deferred to M2, because no addon
  exists. Shared field names do not establish parity.
- The schema is structurally looser than Rust in documented ways: byte lengths,
  fractional integers, duplicate keys and cross-field rules. Rust is
  authoritative.
- Domain errors nested in snapshot or plan records surface as `INVALID_INPUT`.
- Not resolved: predicate-only references, objective participants,
  cross-dataset references and graph analysis (M3).
- Plan addon text limits (32 KiB) belong to the M2 transport. The 4 MiB and
  16 MiB limits are engineering limits.
- Native desktop, packaging and live WoW behavior remain unverified. All
  fixture data is synthetic.
