Environment setup required before any of the above could run, since this
dev host had no Rust or pnpm preinstalled:

- Installed `rustup` from `https://sh.rustup.rs` (`--profile minimal
  --default-toolchain none`); `rust-toolchain.toml` then auto-resolved and
  installed Rust 1.99.0 on first `rustup show`/`cargo` invocation.
- `corepack enable --install-directory "$HOME/.local/bin"` was needed
  instead of a bare `corepack enable`, because `npm config get prefix`
  resolves to `/usr/local`, owned `root:root` mode `755` — a non-root
  global shim install would have failed with `EACCES`. This is a
  dev-host-only quirk, not something encoded into any repo file.
- The preinstalled `corepack@0.24.0` could not run pnpm 12.11.2: it threw
  `Cannot find module '.../12.11.2/bin/pnpm.cjs'`, because that pnpm
  release ships a single compiled `pnpm` binary rather than the legacy
  `bin/pnpm.cjs` layout corepack 0.24.0 expects. Fixed by installing
  `corepack@0.36.0` via `npm install -g corepack@latest --prefix
  "$HOME/.npm-global"` and putting that ahead of the stale one on `PATH`;
  `corepack use pnpm@12.11.2` then succeeded. Recorded here so a future
  session doesn't have to re-diagnose this if the same base image is reused.

Mocked UI, native Windows, and live WoW checks: not applicable — no UI,
desktop package, or addon code exists yet.

## Limitations

- No CI (M1.6): the verification above is local-only and not automatically
  enforced on future changes.
- No real domain logic, contracts, UI, or storage — only two dependency-free
  placeholder crates and empty workspace configuration.
- Not verified on native Windows (plan section 5.2) — this session ran on
  a Linux/WSL dev host.
- `pnpm-lock.yaml`'s only real content is pnpm's own self-managed-binary
  entry; it says nothing about frontend dependency resolution, since no
  frontend package exists yet.
