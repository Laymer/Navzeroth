## Delivered behavior and decisions

A party has one bounded durable active proposal. The proposer explicitly chooses
their local profile and submits the reviewed manual joint request; no participant
is automatically accepted, including the proposer. The service recomputes under
one store lock, requires a selected jointly feasible objective, verifies exact
member snapshot/revision/freshness guards and stores schema 1, a SHA-256 proposal
identity, deterministic result fingerprint, selected objectives and manual time
assumptions. This is a local application document, not a new exchange schema.

Every mutation supplies the expected proposal ID and monotonically increasing
agreement revision. Immediate SQLite transactions compare-and-swap initial
creation, replacement and acceptance/withdrawal. A stale acceptance cannot replace
another member's declaration or accept a superseded plan. Replacement resets all
acceptances. Explicit withdrawal remains available when advice is invalidated.
Deletion cascades the party's proposal only; character data stays intact.

Each read revalidates membership, full data context/fixture, current snapshots,
active content revision, capture freshness and the deterministic joint result.
Changed or unavailable inputs retain the previous declarations as history while
marking the agreement invalidated; they never stay current agreement. There is
no nested service lock. Recalculation enforces candidate/exclusion/member bounds
before evaluation. Stored JSON is size-bounded and typed, checked on read, and
never executed. The document reader checks byte length before allocating it.

Per-member differences compare quest phase/objective status and value, preserving
unknown/restricted/false; timestamp-only recapture does not invent progression.
Original/current observations remain inspectable for actual semantic changes.
Snapshot replacement invalidates even if quest values are unchanged: those are
new inputs requiring another proposal and explicit acceptance.

The Party UI shows the exact proposed objective IDs, goal, origin, stopping
point, time budget, source revision/snapshots and request for review before
per-member acceptance. It labels declarations as local, with no remote identity
claim. Refresh supersedes old async responses; guard-conflict failures refresh
authoritative agreement instead of presenting a stale accepted result.
